# Jev-controlled playtest prototype

The isolated test mod exposes decisions through a loopback HTTP server. A Python controller calls Typesafe Jev, submits one offered action ID, and waits for the next decision. The actual Slay the Spire 2 engine resolves card costs, effects, enemies, draws and rewards. No gameplay rules are reimplemented in Python.

This is a test-only extension to `OvernightHarness`, enabled only by `DEALMAKER_REMOTE=1`. It is not included in Dealmaker releases. The normal game, saves, pending art approvals, and production mod version are unchanged.

## Run it

Configure `TYPESAFE_API_KEY` in your local shell environment; never put the key in this repository or a prompt. The scripts read it at runtime and do not log authorization headers. From the project directory:

```sh
python3 scripts/run_jev.py --id jev-balanced-01 --seed JEVTESTA --strategy balanced --max-decisions 1000
```

Other strategies: `boast`, `wall`, `favor`, `bargain`. `--strategy-file /absolute/path/prompt.txt` supplies a custom strategy. `--model` can pin a model version you have access to; the default is `jev-latest`. `--timeout` bounds wall time. Each run ID must be unique. The existing isolated runner must be present, and the test harness compiled:

```sh
DOTNET_CLI_HOME=.tooling/home .tooling/dotnet/dotnet build tests/overnight/OvernightHarness.csproj --no-restore -c Release -p:UseSharedCompilation=false
```

For a transport-only check, add `--mock`. This makes no Typesafe calls and uses a deliberately crude first-action pilot. It must never be labeled Jev performance or used to estimate balance. Runs remain sequential because the existing runner has one locked test profile. Parallel games require separate cloned runners, profiles and ports.

`--replay /absolute/path/jev-decisions.jsonl` replays saved choices and rejects mismatching observations. The same seed, binary versions, strategy and action log are needed for a meaningful replay. A game seed makes game RNG reproducible; it does not make fresh model decisions deterministic.

## Decision protocol

- `GET http://127.0.0.1:18765/state`: returns `starting`, `busy`, `decision`, `stopped`, or `terminal`.
- A decision contains a unique `decision_id`, `kind`, observed state, and `actions`, each with an ID and semantic description.
- `POST /action` with `decision_id` and `action_id`: validates membership and consumes the decision exactly once. Old or duplicate IDs return 409; unoffered actions return 422.
- `POST /stop`: requests a stop at the current or next decision boundary. A budget stop is not a completed run.
- All requests require the per-run bearer token generated by the launcher. Only loopback is bound; browser Origin requests are rejected. Action requests use fixed-length JSON bodies of at most 4096 bytes.
- HTTP threads operate on serialized snapshots and completion sources. Engine objects are inspected and acted on through the game thread's async continuation.

Combat options include playable cards paired with valid targets, usable potions, potion discard and end turn. Card affordability alone is not sufficient: the engine's `CanPlay` and target checks also enforce restrictions such as IOUs. The next observation is rebuilt after execution. Nested Favor modes, Wall spending, exhaust selections and Bargain targets use the same bridge. Multi-card selections occur one card at a time with a finish option when the minimum is satisfied.

State includes hand, energy, HP, Block, powers and descriptions, Boast progress, enemies and displayed intents, deck, relic descriptions, potions, and unordered draw/discard/exhaust contents. Draw order and future random outcomes are not supplied. Cards have actual descriptions, upgrade state, keywords, costs and dynamic variables; targeted attacks include the engine's per-hit damage calculation where available. That preview is not a full simulation of conditional/multihit outcomes.

Adapters are also implemented for map routes, reward picks/skips, relics, rests, upgrades, removal/transformation/enchantment, shops, events, bundles and Crystal Sphere. Shop removal can open a nested selection. Unsupported or unresponsive screens stop with diagnostics instead of silently falling back to the old heuristic pilot.

## Evidence and current limits

- Build passes with zero warnings/errors.
- Nine Python checks validate Jev request/response handling, action IDs and replay fingerprints.
- Ten HTTP protocol checks validate authentication, illegal/stale/duplicate actions, cancellation and Origin rejection.
- `jev-bridge-smoke-04`: 147 real-engine decisions, five monster rooms, four card rewards, 13 nested selections, ending in ordinary death on floor 5. Normal save hash unchanged. This used the mock transport pilot, not Jev.
- The first tests exposed and fixed map-transition and rewards-to-map timing errors. Budget-stop timing was also corrected.
- Live Typesafe calls have **not** been tested. The local `.env.local` key is now available to the controller; the headed-mode verification deliberately used mock mode.
- The rarer screen adapters, shop transactions, potion actions, late-act events, full-run replay and victory path still need targeted real-engine coverage. Compiling an adapter is not evidence it works on every encounter. Do not yet schedule unattended overnight Jev batches.
- Jev is a decision model, not a freeform narrator. We store its selected action, confidence and full probability distribution; we do not invent prose reasoning. Confidence is not a probability that the move is optimal or that the run will win.
- The inherited engine AutoSlay supervisor has a 25-minute overall run limit; a longer Python timeout does not currently extend it.

## Artifacts

Each run directory under `docs/playtests/runs/<id>/` contains the isolated engine logs and save archive, version/hash manifest, `jev-decisions.jsonl`, `controller.log`, `result.json`, and `jev-summary.json`. The summary reports actual model identifiers, tokens reported by the API, median decision latency, decision categories and low-confidence counts. Request/response records enable later human or agent review of sequencing mistakes and card interactions. Mock/replay mode is labeled explicitly.

## API sources checked September 19, 2026

- [Typesafe HTTP reference](https://docs.typesafe.ai/api): `POST https://api.typesafe.ai/v1/systemone`, bearer authentication, `state`, `model`, `questions`, and `answers`.
- [Choice primitive](https://docs.typesafe.ai/primitives/choice): named criteria, selected option, probabilities and confidence; maximum 255 options.
- [Introduction](https://docs.typesafe.ai/introduction): favors atomic decisions; long-horizon planning ability is a hypothesis to test here, not an assumed capability.

The controller fails on malformed/unoffered answers and API failures. It does not silently substitute a heuristic. There is no need for Jev to access a public web server: Python calls the cloud API and talks to the local game on its behalf.

## Watching the game

The launcher reads `TYPESAFE_API_KEY` from the project `.env.local` automatically (an existing environment variable takes precedence). It reads this file as data, never as shell commands. The game subprocess does not receive the API key; the Python controller loads it when making live calls.

```sh
# Watch a live Jev run in a window, with a one-second pause before each action:
python3 scripts/run_jev.py --id jev-watch-01 --seed JEVTESTA --headed

# Same engine/controller, without a game window:
python3 scripts/run_jev.py --id jev-background-01 --seed JEVTESTA --headless

# Slow down decisions for watching:
python3 scripts/run_jev.py --id jev-watch-slow-01 --seed JEVTESTA --headed --decision-delay 2
```

Headless remains the default. Headed requests a 1280×720 window; it may receive focus when macOS opens it. Both modes use the same isolated test profile and cannot run concurrently against it. Avoid playing cards manually during an automated run because that can invalidate a pending decision. Decision delay changes controller pacing, not the underlying game animations. Each run manifest records the display mode.

Headed verification: `jev-headed-smoke-02` opened the native game window using the Metal renderer and completed eight HTTP decisions (map, combat and nested selection), then stopped at its configured budget. The normal save remained unchanged. The test mod gives initial rendered room loading a bounded 90-second allowance; ordinary gameplay waits are unchanged. Eleven Python checks pass.

## Compact Jev inputs (September 19)

The first optimization used `compact-v1` (superseded by `decision-v2`; see [MODEL-HARNESS.md](MODEL-HARNESS.md)): each distinct complete card definition appears once per request, piles/options reference it, and legal options appear only in question criteria. Cost changes, upgrades, preview damage and targets are preserved. Full observations remain in the logs. Sole-legal-action decisions execute without an API call and are labeled `source: sole_legal_action`; summaries separate their count from model calls and exclude them from model latency.

All 199 decisions from `jev-donaldtrump-headed-01` round-tripped back to the original state and options. The same trace would use 52.1% fewer request characters, including skipped sole-option calls. One actual Jev validation request (decision 2) used 2,496 input tokens instead of 4,779. This is not evidence that play quality is unchanged; compare future runs separately. The headed-03 run was launched before this change and used the original request format.

## Interactive real-game replay prototype

```sh
python3 scripts/watch_replay.py docs/playtests/runs/jev-donaldtrump-headed-01 --at 28
```

Uses the isolated game clone, no Steam/cloud saves and no Jev calls. A Godot overlay provides Back, Play/Pause, Step, delay selection, and a move-number seek. Positions refer to the state **before** the recorded action. Nested card choices are individual moves. No images/video are recorded for replay.

Forward seek executes recorded actions in place. Backward seek now resets the disposable run inside the same game process and reconstructs the target from the seed; it keeps the window open but is slower than checkpoints. It is not a reverse simulation. Game animations still take time during seeking. The launcher verifies the Dealmaker DLL matches the recorded one; the replay uses the updated test harness for its controls and checks recorded observations and actions at each boundary. A changed game version can fail these checks. Actual engine checkpoint support is future work.

The only comparison exception is `NMapScreen.state.text`: the decorative act heading fades in asynchronously and is redundant with structured map/act data. The original observation hash is still verified; other screen text and all gameplay data remain checked. Divergence stops the replay rather than substituting actions.

Replay session metadata/control files live under `docs/playtests/replays/`. In-process seeks are recorded as replay_seek events in the same log; repeated decision IDs are replay visits, not model calls. The controller time budget remains applicable. See Mission Control below for the connected dashboard implementation.

## Mission Control (September 19 implementation)

The Mission Control dashboard now supersedes the style prototypes and connects
the run table, full decision trace, exact request/response viewer, character
selection, game launch, and real-engine replay controls.

```sh
python3 scripts/mission_control.py --port 18766
# Open http://127.0.0.1:18766
```

Use **Launch playtest** to select Dealmaker, Ironclad, Silent, Regent, Necrobinder,
or Defect. Base characters currently offer the balanced strategy; the named
Boast/Wall/Favor/Bargain profiles are scoped to Dealmaker. Character selection is
recorded in the manifest and passed through replay reconstruction. Base characters
receive generic rules plus their own card/power text, Stars, orb slots and orb
order, and Osty's state. Three-decision engine smoke tests passed for all five
base characters, with zero API calls and the normal save unchanged. These tests
verify setup and early actions, not full-run play quality.

The **Game replay** bar controls the actual game. **Step →** executes one recorded
action; **← Back** reconstructs inside the same window and seeks to the previous decision; **Play/Pause** and
**Delay** control pacing; **Move / Go** seeks to a numbered decision. **Close
replay** releases the isolated profile before another test. Inspect a run and use
**Replay selected move in game** to launch it (or seek the same active replay).

The original game toolbar never reliably initialized: this plain .NET mod does
not generate Godot script dispatch for `_Ready`/`_Process`. The replacement builds
native nodes using a deferred callable and updates via a native Timer signal.
The `replay_overlay_ready` event confirms construction. Dashboard transport is
also available independently of the game toolbar.

**Prompt examples** contains four exact requests: three from headed-01 and the
actual compact-request API validation (explicitly labeled as not executed in the
game). Full requests remain accessible at every model-backed decision. Automatic
single-option actions and replay actions correctly display that no API call was
made. Models, strategy text, usage and confidence are preserved.

The service binds only to 127.0.0.1. Mutations require matching Host, Origin and a
per-session CSRF token. The API key is loaded by the controller and never served
to the browser. Character/strategy/run paths are allowlisted; the existing profile
lock prevents concurrent runs. Smoke tests/replays are separate from Jev balance
evidence, and displayed costs are estimates for recorded run usage, not the
account billing total.
